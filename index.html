The Problem: OpenShift Ops at Scale

Alert fatigue, manual investigation, no closed-loop verification

500+Alerts / SRE / week
70%Repetitive (known fix)
47 minAvg MTTR
80%Time spent investigating
Today's Workflow
  1. Alert fires (Prometheus / OCP Event)
  2. PagerDuty pages on-call engineer
  3. Engineer wakes up, opens laptop
  4. Reads alert, opens Grafana dashboards
  5. Runs oc logs, oc describe, oc get events
  6. Identifies root cause (15-20 min)
  7. Executes fix (oc rollout undo, oc scale)
  8. Hopes it worked, goes back to sleep
What's Broken
  • Alert fatigue: 70% repetitive = noise, missed real issues
  • Tribal knowledge: Best engineer's mental model isn't codified
  • Investigation bottleneck: 80% of MTTR is figuring out what's wrong
  • No verification: "I restarted it" but did the problem resolve?
  • Compliance gap: Manual changes lack audit trail
  • Scaling problem: More clusters = more pages, same team

Kubernaut: Intelligent Remediation for OpenShift

Kubernetes-native operator with LLM-powered investigation agent

Operator Pattern (controller-runtime)
  • 10 Custom Resource Definitions on kubernaut.ai/v1alpha1
  • CRD-driven state machine: Pending → Processing → Analyzing → Executing → Verifying
  • Owner references for cascading lifecycle (parent deletes children)
  • Leader election + namespace-scoped cache per controller
Agent Architecture (LLM + Tools)
  • Multi-turn LLM tool loop: RCA phase + Workflow Discovery phase
  • Tool registry: kubectl, Prometheus, logs, AlertManager, fleet MCP
  • Shadow agent alignment: prompt injection detection (fail-closed)
  • MCP interactive mode: human takeover mid-investigation

Operator Internals: CRD-Driven State Machine

RemediationRequest lifecycle on OpenShift (controller-runtime reconciliation)

CRD State Machine
  • Each phase creates a child CRD (SP, AIA, WFE, EA)
  • Orchestrator watches child status via controller-runtime
  • Phase transition recorded as K8s Condition + audit event
  • Global timeout (1h) + per-phase timeouts (5m/10m/30m)
  • Blocked phase: resource busy, backoff, unmanaged scope
Operator Components (5 controllers)
  • SP Signal Processing: K8s enrichment + Rego policy eval
  • AIA AI Analysis: dispatches to Kubernaut Agent HTTP API
  • WFE Workflow Execution: Tekton/Job/Ansible backends
  • EA Effectiveness Monitor: pre/post metric comparison
  • NR Notification: multi-channel delivery CRD controller
OpenShift-Native Deployment
  • helm install kubernaut ./charts/kubernaut
  • All CRDs: oc get rr,sp,aia,wfe,ea,nr
  • Namespace-scoped cache (ADR-057)
  • Leader election for HA
  • OCP TLS profiles + cert-manager integration

SPEAKER NOTES -- Slide 3 (12:00 - 18:00)

Opening: "Now let me show you how the operator actually works under the hood. This is the lifecycle of a single remediation."

Walk the state machine:

  • "When Gateway creates a RemediationRequest CRD, it starts in Pending. The Orchestrator picks it up and creates a SignalProcessing child CRD -- that's the Processing phase."
  • "Once Signal Processing completes enrichment and classification, the Orchestrator creates an AIAnalysis CRD -- that's Analyzing. The AI Analysis controller dispatches to the Kubernaut Agent for investigation."
  • "If confidence is below threshold -- say 75% for a production namespace -- it goes to Awaiting Approval. A RemediationApprovalRequest CRD is created, and a Notification CRD sends a Slack message. An operator approves or rejects."
  • "If confidence is high enough, it skips straight to Executing -- that dashed blue line. A WorkflowExecution CRD is created. The WFE controller creates a Tekton PipelineRun or K8s Job."
  • "After execution succeeds, it moves to Verifying. An EffectivenessAssessment CRD is created. The EM controller checks: is the alert resolved? Are pods healthy? Are metrics back to baseline?"
  • "Only after verification passes does it reach Completed."

On the Blocked phase: "If there's already an active remediation on the same target resource -- say two alerts fire for the same deployment -- the second one goes to Blocked (ResourceBusy). It waits for the first to complete, then proceeds. This prevents conflicting concurrent modifications."

Key operator pattern points:

  • "Every phase transition is a Kubernetes status update with a condition. You can see exactly where a remediation is with 'oc describe rr [name]'."
  • "Owner references mean when the parent RR is deleted, all children cascade-delete. Kubernetes garbage collection handles cleanup."
  • "Each controller uses a namespace-scoped informer cache -- it only watches the kubernaut-system namespace. Minimal API server load."

If someone asks about scaling: "Each controller is independently scalable with leader election. The Orchestrator handles the coordination logic. If you have 1000 alerts/min, you can scale the Gateway and Signal Processing horizontally while the Orchestrator manages sequencing."

Timing: 5-6 minutes. The state machine diagram is the key visual -- trace through it while talking.

Safety, Compliance, and Control

Built for regulated environments -- SOC2/FedRAMP audit-ready, deny-by-default

Human-in-the-Loop Approval Gates

Confidence-based: <80% requires operator approval via Slack/console. Configurable per namespace, per action type. RemediationApprovalRequest CRD tracks decision + actor.

Immutable Audit Trail (ADR-034)

Every event: hash-chained, timestamped, actor-attributed. Stored in PostgreSQL with 7-year retention. Full RR lifecycle reconstructable from correlation_id alone. SOC2 CC8.1 compliant.

Scope Management (deny-by-default)

Only namespaces labeled kubernaut.ai/managed=true are visible. Resources without label are rejected at Gateway. Multi-cluster: per-cluster scope via fleet registry.

Shadow Agent Alignment (ADR-KA-001)

Independent LLM evaluates every investigation step for prompt injection or anomalous behavior. Fail-closed: circuit breaker terminates investigation on suspicious verdict.

Consecutive Failure Protection

After 3 failed remediations on same target: phase transitions to Blocked, 1-hour cooldown, escalation notification. Exponential backoff: 1m, 2m, 4m, 8m, 10m cap.

Effectiveness Verification

Post-execution: checks alert resolution, pod health, Prometheus metrics, spec hash drift. Scores effectiveness 0-100. Inconclusive outcomes trigger exponential backoff on retry.

Compliance mapping: SOC2 CC8.1 (audit completeness) | CC6.1 (financial governance) | CC7.2 (decision trails) | FedRAMP AU-2/AU-3 (event content) | AU-9 (protection) | AU-11 (retention) | AC-6 (least privilege)

SPEAKER NOTES -- Slide 4 (18:00 - 24:00)

Opening: "Safety isn't an afterthought in Kubernaut -- it's the architecture. Let me walk through six layers of protection."

Approval gates: "Like a pull request for infrastructure. The AI proposes, humans approve. The threshold is configurable -- you might set 90% for production and 70% for dev. Below threshold: mandatory approval via Slack. Above: auto-execute for low-risk actions. The RemediationApprovalRequest CRD records WHO approved, WHEN, and WHY."

Audit trail: "This is critical for compliance. Every action produces an immutable event in PostgreSQL. Events are hash-chained -- tamper with one and the chain breaks. Given a correlation_id, you can reconstruct the ENTIRE remediation lifecycle: what alert fired, what the AI investigated, what it decided, who approved, what executed, what the outcome was. This maps to SOC2 CC8.1 directly."

Scope: "Deny-by-default. If a namespace doesn't have the managed label, Kubernaut can't see it. Period. Gateway rejects signals from unmanaged namespaces at the front door. For multi-cluster: each managed cluster is registered separately."

Shadow agent: "This is unique. A second, independent LLM watches the primary agent's investigation. It evaluates every LLM response and every tool call for signs of prompt injection or anomalous behavior. If it flags something suspicious, a circuit breaker terminates the investigation immediately. Fail-closed -- not fail-open."

Consecutive failures: "If the same issue fails remediation 3 times, Kubernaut stops. It transitions to Blocked, applies a 1-hour cooldown, and pages a human. It won't thrash your cluster."

Verification: "Every remediation is verified. The Effectiveness Monitor checks: did the alert resolve? Are pods healthy? Are latency metrics back to normal? It produces a 0-100 effectiveness score. If the score is low or the alert is still firing, it marks the outcome as Inconclusive and applies exponential backoff before the next attempt."

Compliance line at bottom: "For anyone dealing with auditors -- every control listed there has a direct mapping in the codebase. AU-2 event generation, AU-3 event content, AU-9 immutability, AU-11 retention. The audit table design was built against these controls from day one."
