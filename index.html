Safety, Compliance, and Control

Six layers of protection -- built for regulated environments from day one

1. Approval Gates

Confidence <80%: mandatory operator approval via Slack/console. RAR CRD tracks who approved, when, why. Configurable per namespace and action type.

2. Immutable Audit Trail

Hash-chained PostgreSQL events (ADR-034). Full lifecycle reconstructable from correlation_id. 7-year retention. SOC2 CC8.1, FedRAMP AU-2/AU-9 mapped.

3. Scope: Deny-by-Default

kubernaut.ai/managed=true label required. Unmanaged namespaces invisible at Gateway. Fleet: per-cluster scope via registry.

4. Shadow Agent Guard

Independent LLM evaluates every investigation step. Prompt injection detection. Circuit breaker: terminates on suspicious verdict. Fail-closed design.

5. Failure Protection

3 consecutive failures: Blocked phase + 1h cooldown + escalation notification. Exponential backoff: 1m/2m/4m/8m/10m cap. Resource locking prevents parallel conflicts.

6. Effectiveness Verification

Post-execution: alert resolution + pod health + Prometheus metrics + spec hash drift. Scores 0-100. Inconclusive: backoff + escalate. Never marks "done" prematurely.

Compliance Controls: SOC2 CC8.1 (completeness) | CC6.1 (governance) | CC7.2 (decision trails) | FedRAMP AU-2 (events) | AU-3 (content) | AU-9 (immutability) | AU-11 (retention) | AC-6 (least privilege) | SI-10 (input validation)

Appendix: Why Not Individual Agents Per Issue?

Architecture decision -- unified generalist + pluggable specialist runtimes (v1.6 roadmap)

Current: Generalist Agent
  • Single agent with broad tool access
  • RCA is GENERIC (what's wrong?)
  • SPECIALIST knowledge lives in the workflow catalog (curated, versioned, schema-validated remediation recipes)
  • Fast: 10-30s for common issues
  • Simple ops: one agent to monitor, one set of metrics
  • Shadow agent alignment works universally
v1.6: Specialist Agents (AgenticWorkflow CRD)
  • Oracle Agent Spec (OAS): Declarative YAML agent definitions compiled to LangGraph
  • Deep Agents: Multi-hypothesis investigation with sub-agent spawning
  • Goose Runtime: Session-based investigation recipes
  • Per-issue-type OCI bundles (e.g., OOM specialist, network specialist)
  • Orchestrator routes to correct runtime based on signal type/severity
  • ACP enforcement layer provides consistent tool access control
Why Both? (Architecture Decision)
  • 80% of alerts: Generalist handles in 10s (known patterns)
  • 20% complex cases: Deep Agent explores hypotheses, spawns sub-agents
  • Orchestrator decides which runtime based on signal classification
  • Shadow agent alignment works across ALL runtimes
  • NOT "one agent forever" -- it's a pluggable runtime system
  • Workflow catalog = fast path; AgenticWorkflow = deep investigation path
RHACM Integration (from codebase)
pkg/fleet/acm/: ACM Search GraphQL for scope checking (/searchapi/graphql)
pkg/fleet/registry/: Kuadrant + EAIGW cluster registry watchers
pkg/fleet/mcpclient/: MCP remote tool calls for investigation + execution
Kubernaut integrates with RHACM -- does NOT replace it
Multi-Agent Objection Response
"Per-issue specialists are the roadmap (AgenticWorkflow CRD, v1.6).
Today's generalist is intentionally simple -- specialization is in the catalog.
For novel/complex cases, Deep Agents already support multi-hypothesis + sub-agents.
The architecture is NOT monolithic -- it's a pluggable runtime system."

The expert challenge you might hear: "Modern agentic architectures use multi-agent systems -- CrewAI, AutoGen, LangGraph multi-agent -- where each agent specializes in one domain. Why does Kubernaut use a single generalist agent?"

Your response (memorize this structure):

  1. "Great question. First, the current agent is intentionally a generalist INVESTIGATOR -- its job is to figure out WHAT'S WRONG. The specialist knowledge is in the workflow catalog -- curated, tested, schema-validated remediation recipes. So we already have specialization, just in the execution layer."
  2. "Second, v1.6 introduces the AgenticWorkflow CRD -- this IS the multi-agent pattern. You can deploy per-issue-type specialist agents as OCI bundles. We have three runtime types validated: Oracle Agent Spec (declarative), LangChain Deep Agents (multi-hypothesis with sub-agent spawning), and Goose (session recipes)."
  3. "Third, the Orchestrator decides which runtime to use based on signal classification. Simple OOM? Generalist handles it in 10 seconds. Complex cross-service failure with no known pattern? Deep Agent explores multiple hypotheses with sub-agents."
  4. "And critically -- the shadow agent alignment check works ACROSS all runtimes. Safety doesn't depend on which agent is investigating."

On RHACM: "Kubernaut integrates with RHACM -- it doesn't replace it. We use ACM Search's GraphQL API for scope checking across managed clusters. The fleet tools use MCP to interact with remote clusters through your existing gateway (Kuadrant or Envoy AI Gateway). It's complementary, not competitive."

If pressed on "why not specialists today?": "Operational simplicity. One agent to monitor, one set of metrics, one failure domain. The generalist handles 80% of cases perfectly. We add specialist runtimes for the complex 20% -- but only when you need them, not by default. Premature specialization is a complexity tax."
